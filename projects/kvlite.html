Overview

A database's hardest promise is durability: once it says "saved", the data must still be there after a crash. I built KVLite to learn how real databases keep that promise, using the same technique as Redis's append-only file and Postgres crash recovery.

Every write is appended to a checksummed write-ahead log before it is applied in memory. On restart, KVLite replays the log. If a power cut left a half-written record, its checksum fails, replay stops there, and the log is truncated back to the last good record. A TCP server speaks a Redis-style text protocol to many clients at once.

Guarantees

ProblemHow KVLite handles it
The process crashes after a writeThe record is already in the write-ahead log, which is replayed on startup.
Power fails mid-writeThe torn record fails its CRC32 check; replay stops there and the log is truncated to the last good record.
A record is corrupted on diskA checksum mismatch means the record is never applied.
Compaction crashes halfwayThe new snapshot is written to a temp file, fsynced, then atomically renamed, so the old or new snapshot is always complete.
Keys or values contain tabs or newlinesKeys and values are base64-encoded in the log, so any text is safe.
Many clients increment one counterStorage operations share one lock, so INCR is atomic.

The core idea in code

Each log record carries its own checksum, so recovery can tell a complete record from a torn one:

def encode(op, key, value="", expires_at=0.0):
    body = f"{op}\t{b64(key)}\t{b64(value)}\t{expires_at!r}"
    return f"{body}\t{zlib.crc32(body.encode()):08x}\n".encode()

Writes are logged before they become visible:

with self._lock:
    self._wal.write(encode("SET", key, value, expires_at))
    self._wal.flush()
    if self.durability is Durability.FSYNC:
        os.fsync(self._wal.fileno())
    self._data[key] = (value, expires_at)

In action

kvlite> SET user:1 Ada Lovelace
+OK
kvlite> SETEX session:42 60 tok_abc
+OK
kvlite> INCR page_views
:1
kvlite> GET user:1
$Ada Lovelace
kvlite> STATS
+keys=3 wal_records=3 recovered=0 compactions=0

Stop the server with Ctrl+C and start it again: every key is still there, and STATS reports how many records were recovered.

The gap is the cost of making the disk confirm every write, a trade-off every database makes. Measured with the built-in benchmark on a small cloud VM; numbers vary by machine.

What the tests prove

  • Data survives restart, including deletes and overwrites
  • A torn write after a simulated crash is truncated, and new writes then succeed
  • A record with a forged checksum is never applied
  • TTL expiry works in memory and across restarts
  • Compaction shrinks the log to zero and keeps every live key
  • 6,000 writes from 6 threads, interleaved with compactions, all survive restart
  • 8 threads × 500 INCRs land on exactly 4,000
  • 10 TCP clients in parallel read back their own writes

Run it

Python 3.10 or newer, no installs needed.

python -m kvlite serve                 # start on port 6380, data in ./data
python -m kvlite cli                   # interactive client in a second terminal
python -m kvlite bench                 # throughput in both durability modes
python -m unittest discover -s tests
