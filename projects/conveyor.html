Conveyor

A distributed task queue that keeps going when workers crash, dependencies time out, or the broker restarts.

Overview

Most web apps push slow work (sending email, resizing images, calling flaky APIs) onto a background queue such as Celery or Sidekiq. I built one from scratch to understand what makes them reliable.

A broker stores every job in SQLite and hands jobs to worker processes over HTTP. Each claim is a time-limited lease: running workers renew it with heartbeats, and if a worker dies, the lease expires and another worker takes the job. Failures retry with exponential backoff, and jobs that never succeed move to a dead-letter queue where a person can inspect and retry them.

Guarantees

ProblemHow Conveyor handles it
Two workers grab one jobA claim is a single atomic UPDATE … RETURNING inside BEGIN IMMEDIATE, so only one worker can win.
A worker crashes mid-jobIts lease stops being renewed and expires; the next claim puts the job back in the queue.
A crashed worker reports lateCompletions are fenced by worker ID, so a stale worker can't overwrite the result of the one that took over.
A dependency is downRetries use exponential backoff with full jitter, capped, so retries don't stampede.
A job can never succeedAfter max_attempts it moves to the dead-letter queue with its last error.
The broker restartsJobs live in SQLite in write-ahead-log mode, so the queue survives.

The core idea in code

Claiming a job is one statement: pick the highest-priority ready job and lease it, atomically.

UPDATE jobs SET status = 'running', attempts = attempts + 1,
                worker = ?, lease_until = ?
WHERE id = (SELECT id FROM jobs
            WHERE status = 'queued' AND run_at <= ? AND queue IN (…)
            ORDER BY priority DESC, run_at, id LIMIT 1)
RETURNING *

Backoff with full jitter spreads retries out instead of hitting a recovering service all at once:

def backoff(self, attempts):
    ceiling = min(self.backoff_cap, self.backoff_base * 2 ** attempts)
    return random.uniform(self.backoff_base, max(self.backoff_base, ceiling))

Chaos demo

python -m conveyor demo starts a broker, launches three worker processes, enqueues 151 jobs (CPU work, flaky calls, slow jobs and one that always fails), then kills a worker mid-job.

$ python -m conveyor demo
Dashboard: http://127.0.0.1:8700
Started 3 worker processes on 151 jobs
  Chaos: killed worker-1 mid-job; its leases expire and other workers pick the jobs up
Finished in 5.8s · 118 done · 20 needed retries · 3 in the dead-letter queue

Every job resolves: completed, retried to success, or dead-lettered with its error. A live dashboard shows queue depth, active workers, per-task latency and a one-click retry for dead jobs.

What the tests prove

  • Priority first, then first-in first-out within a priority
  • Delayed jobs are never claimed early, and named queues stay isolated
  • 8 threads racing over 300 jobs claim each job exactly once
  • An expired lease is redelivered, and the stale worker is fenced out
  • Heartbeats keep a long job's lease alive
  • Retries back off, then dead-letter; a dead job can be retried
  • Jobs survive a broker restart
  • End to end over HTTP with multiple workers

Run it

Python 3.10 or newer, no installs needed.

# see everything at once
python -m conveyor demo

# or run the parts yourself
